# sinopac-deck 架構分析與 v4 改版說明

> 2026-07-17。基準＝上傳的 v3 skill（repo 首個 commit）；本文對應三個提問：
> ①文案→HTML 的 token 效率、②模板呈現優化、③寫作指引深化（行數上限）。

---

## 〇、v3 的 token 都花去哪了（實測）

| 檔案 | 大小 | 內訳 |
|---|---|---|
| assets/template.html | 70.0 KB | 引擎 CSS 28.7 KB＋**logo base64 14.8 KB**＋示範頁 body 19.8 KB＋JS 4.4 KB |
| SKILL.md | 16.7 KB | — |
| references/writing.md | 9.6 KB | — |

v3 的 S2（組裝）要求模型 `cp` 模板後用編輯工具刪版型、複製版型、逐槽填字。實際成本（12 頁估）：

| 階段 | v3 | 說明 |
|---|---|---|
| S2 讀模板 | ~18–20k tokens（輸入） | 整檔 Read：base64 ≈ 3.7k、引擎 CSS ≈ 8k、示範 body ≈ 7–9k |
| S2 編輯輸出 | ~10–18k tokens（輸出） | 複製版型＝整段重打；每次取代＝舊字串＋新字串各付一次 |
| S3 驗收重讀 | ~5k tokens | 抽頁核對、grep 佐證 |
| **機械段合計** | **~35–45k tokens** | **全部與內容品質無關**，且 >8 頁還要分輪、每輪重付模板閱讀 |

長輸出末段品質衰減是真問題，但 v3 的解法（分輪）治標：真正的病因是**讓模型輸出 HTML**。

## 一、文案→HTML：改成「模型只寫文字，腳本組 HTML」

**v4 核心改動：新增 `scripts/build_deck.py`。** S1 的 `content.md`（結構化槽位格式，
見 `references/content-example.md`）直接餵給腳本，deterministic 地產出 deck.html——
引擎從模板原樣複製、頁碼/頁尾/結論列/網格變體全自動、占位字自檢附帶完成。

| 階段 | v3（12 頁） | v4（12 頁） |
|---|---|---|
| S0 骨架 | 2–3k | 2–3k |
| S1 文案 | 4–6k | 5–7k（行數預算制，內容更滿） |
| S2 組裝 | 28–38k | **~0.3k**（跑兩行指令） |
| S3 驗收 | ~5k | ~1k（lint＋`?debug` 溢出檢查） |
| **合計** | **~40–52k** | **~9–12k（省約 75%）** |

**「一次對話能不能出完？」——能。** 15 頁的 content.md 只有 4.5 KB（≈3–4k 輸出 token），
遠低於長輸出衰減區；一輪內可完成 S0→S1→build→verify。分階段只保留一個目的：
**S0 骨架核可是品質閘門，不是 token 措施**——>10 頁或素材模糊時先給使用者過目故事線，
短小明確的案子併一輪直接出。

配套省 token 措施：

- **logo base64 移到檔尾** `style#brand-assets`：部分讀取模板時不再吞 ~4k token 的無資訊字元。
- **`build_deck.py --schema <版型>` 自我文件化**：查槽位不用讀模板（每次省數千 token）。
- SKILL.md 明訂鐵則：template.html／deck.html **禁止整檔 Read**，查頁面用 grep。
- 手動組裝仍保留（blank 自訂版面），但降級為例外路徑。

## 二、模板呈現優化

### 2-1 頁尾瘦身，釋放內容高度

| 參數 | v3 | v4 |
|---|---|---|
| 頁尾底距 | 2.6cqh | **1.6cqh**（更貼邊） |
| LOGO 高 | 4.6cqh | **3.6cqh**（更小；母片規格「只縮不放」仍守） |
| 內容區下緣保留 | 10.5cqh | **7.6cqh** |
| 內容區上緣＋頁首間距 | 4cqh＋較鬆 | **3.4cqh＋收緊** |

合計釋放 **~4.4% 版高 ≈ 多 1–2 行內文**；LOGO 帶從「底部 94%」移到「95–97%」、
右緣 97%（反而更貼母片原始定位）。頁尾字級仍守 .78em 下限，手機版不受影響。

### 2-2 結論先行區塊：全內容頁固定配備 `.bluf`

v3 只有 prose 版型有結論色塊；v4 升為通用元件——每個內容頁標題下固定一條結論列：

- 1–2 行（硬上限 3 行）、24–70 字；前置章 chip（結論／建議／請示…）。
- 藍＝結論/建議；「請示／行動／決議」自動轉紅（紅＝行動的官方色語意）。
- 寫作規則（writing.md §〇）：**標題的補完，不是複述**——lint 會算標題 2-gram 重合率，≥70% 警告。
- 讀者只讀「標題＋結論列」就能散會，即為合格。

### 2-3 頁面必要性檢視：15 版型全留＋新增 1

逐一檢視後**不砍版型**——版型庫本身不再是 token 成本（腳本組裝、不用讀），砍庫只會逼
內容硬塞錯的版型。調整的是「用法」：quote 每副 ≤1 張、case 指令框維持選用、等分卡片
只在真序列（Q1→Q4）合法。

**新增 `ask` 決議頁**：內部報告最關鍵、v3 卻缺席的一頁——「要老闆決定什麼」。
左欄 2–4 條請示事項（編號＋行動句＋依據），右欄關鍵條件（時限/預算/範圍），
配紅色「請示」結論列。BLUF 文化裡這頁通常直接決定會議成敗。

### 2-4 核心內容區塊重塑（參考其他視覺設計 skill）

分析了內建 `dataviz` 與 `artifact-design` 兩個 skill，借用三條原則落地：

1. **dataviz「一個視圖只有一個 hero figure」＋ stat tile 契約（label/value/delta/trend）**
   → cards／kpi 新增 `lead` 首格主從修飾（`has-lead` 網格 1.45fr＋首格放大、紅漸層淡底）
   與 `n3` 三格變體，讓「一頁一焦點」從口號變成一個 flag 就能做到的版式。
2. **artifact-design「等大圓角卡＋色條＝AI 樣板臉」「結構編號必須承載真實資訊」**
   → SKILL.md 的反等分規則現在有了模板級支援；等分僅保留給真序列。
3. **主元素不動**：品牌外框、紅線母題、官方色、16:9 引擎、頁尾規格全數未動——
   重塑只發生在內容區塊內部。

工程修正（附帶）：optiontabs 改支援同副多實例；`.bluf.act`／`.lead` 與既有卡片類別
撞名的 bug（會把結論列排成直欄、KPI 格矮一截）改名為 `.bluf.red`／`.is-lead`；
列印註解仍寫「A4 橫式」的過時文字改為 16:9 滿版。

## 三、寫作指引深化：從「單行字數」到「行數預算」

v3 只管每行字數上限，結果就是你觀察到的：**文案傾向每格只給一行，卡片明明能載 5 行**。
lint v2 對 v3 自帶的示範文案跑一次，立刻抓到 4 張單行卡片（21–26 字，預算 5 行）——現象實錘。

v4 的三層解法（writing.md §二、§二之二）：

1. **元素級「字/行 × 行數 → 字數帶」全表**：每個槽位標注 1080p 實測的每行字數
   （卡片說明 14 字/行、lead 卡 18、對照條列 26、prose 段 34、結論列 58…）與行數上限，
   寫作順序改為「先決定行數、再換算字數」。
2. **各版型行數預算＋填充率 60–90%**：卡片說明 2–5 行（≥2 個資訊點）、對照每側 10 行、
   KPI 說明 1–3 行、prose 兩欄 32 行……填不滿就放大焦點，不硬湊空話。
3. **密度紅綠燈自動化**（lint_content.py v2）：逐頁估行數，過疏（單行卡片型浪費）與
   過密（會溢出）都警告；同清單行數須一致（全 1 行或全 2 行，長度差 >8 字才報）；
   條列從「一行收掉」放寬為「1–2 行、同清單一致」。

